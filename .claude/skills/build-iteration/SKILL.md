# build-iteration

Builds one Iteration of the saas-handson curriculum as a pair of independent cabal packages under `iterations/iteration-N/{exercise,solution}/`. Iteration 0 (`iterations/iteration-0/`) is the first applicant of this pattern; every later Iteration must match the design principles, directory layout, and verification procedure established there.

## When to use

Use this when asked to create the exercise and solution projects for the next Iteration of this curriculum (e.g. "build Iteration 1", "hands-on-ify Iteration 2").

## Scope

- Always covers exactly **one** Iteration per invocation. Do not build multiple Iterations in one pass.
- The target Iteration number N is the next one after the last completed Iteration.
- Deleting the old cumulative `saas-handson` / `saas-handson-solution` packages and the final cleanup of the root `README.md` / `cabal.project` once every Iteration is done is **out of scope**. That happens as a separate, manual step after the whole curriculum is migrated.

## Sources of truth

- What to implement in each Iteration, and why, comes only from the corresponding section of `docs/ROADMAP.md` ("実装する機能" / "含むリファクタリング" / "目的").
- Do not copy prose, comments, or test code from the old cumulative `saas-handson` / `saas-handson-solution` packages or their `docs/iteration-N.md`. That old structure was written before Iterations were split apart, so its TODO comments and type signatures already assume later Iterations' shapes — carrying that over would reintroduce the exact "later Iteration leaked into this one" problem that Iteration 0 was rebuilt to fix. Write the exercise instructions, solution explanations, and test code fresh, using only the ROADMAP.md feature list as the spec.
- The **previous Iteration's solution package** — code and tests together — is the one thing that should be carried forward as-is, and the mechanical way to do that is to literally copy the directory (`cp -r iterations/iteration-(N-1)/solution iterations/iteration-N/solution`, and again into `.../exercise`), not to retype it by hand. It is the working baseline the learner builds on. What gets newly authored is only the increment (new feature or refactor) that ROADMAP.md describes for this Iteration, plus the prose (`docs/iteration-N.md`, `README.md`), which is never copied — see above.

## Design principles (established while building Iteration 0)

1. **Each Iteration project is a complete, working snapshot of everything that should exist by that Iteration.** Whatever a previous Iteration introduced is handed over as finished code; only the new part introduced by this Iteration is TODO/exercise material.
2. **Never leak a later Iteration's shape into an earlier one.** Type signatures, function arguments, and module structure must not anticipate a later Iteration's design (e.g. taking a `Logger` or `Repository` argument before that Iteration exists). Comments should only describe what exists as of this Iteration; a brief forward-looking sentence ("a later Iteration will add...") is fine, but signatures and implementations themselves must not pre-adopt it.
3. **Tests belong to features, not to Iterations, and whatever this Iteration does to a feature's tests is exercise material.** A spec file (`Health/HealthSpec.hs`, `User/UserSpec.hs`, `Auth/AuthSpec.hs`, ...) exists for as long as its feature exists. Only a genuinely new module/feature introduced by this Iteration gets a new spec file (Health in Iteration 0, User in Iteration 1, Auth in Iteration 2, ...); when this Iteration instead changes a feature that already exists, the work happens in that feature's existing spec file — adding new `it` cases, or revising an existing one whose expectation the change alters — never in a separate `IterationNSpec.hs`.
   - Whether this Iteration calls for a new spec file or a revision to an existing one, the exercise package's copy of that file must stay exactly as carried over from the previous solution (untouched, since it was never edited) — none of this Iteration's new or changed test cases are in it, and no `other-modules` entry points at a file that doesn't exist yet. `docs/iteration-N.md` (exercise) must describe concretely what to add or change there (expected status codes, response bodies, edge cases) before the learner implements anything.
   - Every such step must also have the learner work out, before writing anything, whether this Iteration's change affects the unit test, the integration test, or both, and explain why — the same question Iteration 0's 演習0-4 already asks when comparing Health's two tests, now recurring for every Iteration's own change, not just the first.
   - (Iteration 0 is the special case where every test is new, so its exercise package ships only the hspec-discover driver stub with no `*Spec.hs` files at all.) The solution package always ships complete, passing implementation and tests, whichever files this Iteration's change touched.
4. **Write positively, never defensively.** Never write things like "this project doesn't depend on...", "...doesn't appear here", or "this project is self-contained and depends on nothing else" — these read as excuses justifying how the material was carved out, not as content the reader needs. State only what this Iteration builds, in positive terms. If the curriculum's overall arc needs mentioning, phrase it forward-looking ("this curriculum expands into X, Y, Z as Iterations progress"), never as an absence.

## Package names and directory layout

- Directories: `iterations/iteration-N/exercise/`, `iterations/iteration-N/solution/`
- Cabal package names: `saas-handson-iterationN`, `saas-handson-solution-iterationN` (**do not put a hyphen before the bare digit** — `saas-handson-iteration-1` fails to parse because cabal rejects an all-numeric hyphen-separated name component; `saas-handson-iteration1` is required. The directory name keeps the hyphen, e.g. `iteration-1`.)
- Name the `.cabal` file after the package (e.g. `saas-handson-iteration1.cabal`).

## Procedure

1. Read the Iteration N section of `docs/ROADMAP.md` for the feature and goal, and the Iteration N-1 section for context on where the previous Iteration left off.
2. Copy `iterations/iteration-(N-1)/solution/` wholesale into both `iterations/iteration-N/exercise/` and `iterations/iteration-N/solution/` (`cp -r`). This is the literal starting point for each — do not retype the carried-over code or tests by hand. In both copies, rename the package (`saas-handson-iterationN` / `saas-handson-solution-iterationN`), rename the `.cabal` file to match, and update the self-referencing `build-depends` (library and executable stanzas) and the `executable` name to the new package name.
3. Read `iterations/iteration-0/` (both exercise and solution) as the reference for `.cabal` conventions, the `docs/iteration-N.md` exercise numbering pattern (N-1, N-2, ... walking through: read/understand, confirm Red by writing your own tests, implement to Green, compare unit vs. integration tests, then an extension exercise), and README structure.
4. Decide, from ROADMAP.md's description, whether this Iteration introduces a genuinely new module/feature (new spec file) or changes a feature that already exists (existing spec file gets new or revised test cases). In the `iterations/iteration-N/exercise/` copy: apply only that new feature/refactor, turning its implementation into TODO in src/app (implementation stubs, `error "TODO: ..."`, hint comments). Leave every other module, and every spec file, exactly as carried over — untouched, whether or not this Iteration will eventually add to or revise that same file. Write `docs/iteration-N.md` (exercise) fresh, including the step that asks the learner to determine whether this Iteration's change affects the unit test, the integration test, or both, before they write or edit anything; write `README.md` fresh too (prose is never copied — see Sources of truth).
5. In the `iterations/iteration-N/solution/` copy: implement that same feature/refactor fully, and update whichever spec file(s) it affects — adding new test cases to an existing feature's file, revising an existing case if the change alters previously-tested behavior, or authoring a new file only if this Iteration introduces a genuinely new module. Write `docs/iteration-N.md` (solution/explanation) and `README.md` fresh.
6. Add both new package paths to the root `cabal.project`'s `packages` list.
7. Run `cabal build` and confirm both packages compile. Remember `{-# LANGUAGE OverloadedStrings #-}` on any module that builds a `Text`-based record from a string literal.
8. Run `cabal test` on the solution package and confirm every test — carried-over and new — is GREEN.
9. Verify the exercise package's TDD cycle actually works for this Iteration's change: temporarily copy the solution's version of whichever spec file(s) it touches into the exercise's `test/unit` and `test/integration` — overwriting the carried-over version if that file already existed there — and, for a genuinely new file, temporarily add the matching `other-modules` entry to the exercise's `.cabal`. Run `cabal test` and confirm it goes RED for the expected reason (the TODO's `error`) while every other, unrelated test still passes. Then **fully restore the exercise package to its shipped state**: put back the exact carried-over version of any file you overwrote (or delete it, if it was a new file), and revert the `.cabal` file. Never leave verification leftovers in the shipped exercise package.
10. Re-run `cabal test` on the restored exercise package and confirm it is back to the intended starting state: every carried-over test still passes exactly as before, and there is no test yet for this Iteration's change.
11. Create or revise the matching chapter in `docs/haskell-reference/`. The numbering is offset by one from the Iteration number (`00-basics.md`, then `01-iteration-0.md`, `02-iteration-1.md`, ... so Iteration N's chapter is `0(N+1)-iteration-N.md`); update the table of contents in `docs/haskell-reference.md` if the chapter is new. Whether creating or revising, hold it to the same bar as `00-basics.md` and `01-iteration-0.md`: concrete, factual explanations grounded in actual type signatures and behavior — no hedging or metaphor dressed up as explanation (e.g. wrapping a vague word like "context" in quotes as a stand-in for a real definition, or reaching for an unrelated-language analogy instead of stating the type and its behavior directly).
    - What a language extension is in general (the `{-# LANGUAGE ... #-}` pragma, `Haskell2010` vs. GHC extensions, what happens if one isn't enabled) belongs once in `00-basics.md`, not repeated in every Iteration's chapter. Each Iteration's own chapter should just list and explain the specific extensions it introduces — no need to cross-reference `00-basics.md` for this.
    - Check every `{-# LANGUAGE ... #-}` pragma that appears for the first time anywhere in this Iteration's newly written or newly modified files (exercise and solution alike). For each one, the chapter must explain concretely what it enables and why the specific line that needs it would otherwise fail to compile — not just note that it's "used here." Determine this from what this Iteration's own code actually needs, not from where an equivalent extension happened to be explained in the old cumulative `saas-handson`/`saas-handson-solution` packages: because each Iteration is now its own snapshot rather than an accumulating whole, an extension can become necessary earlier than it did there (for example, `OverloadedStrings` and `QuasiQuotes` were already required in this curriculum's Iteration 0, well before the old structure needed them).
12. Run a `/sanitize-artifacts` pass over everything newly written or changed in this Iteration (both projects' `README.md`, `docs/iteration-N.md`, source comments, and the haskell-reference chapter). Check especially for the defensive phrasing covered in design principle 4, and for any other trace of the conversation or production process.

## Troubleshooting

- Right after editing a `.cabal` file, `cabal test <package-name>` (with no component qualifier) can fail with `Ambiguous target ... exe:X (component) / lib:X (component)`. This is not a problem with the file — it's a stale `dist-newstyle` build-plan cache. Run `cabal clean`, then rebuild and retest.
